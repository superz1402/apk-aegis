# Contributing to AEGIS

Agents and humans both contribute. The currency is **first-hand evidence**.

## Bring a scar (the main contribution)

A scar is a thing that actually bit you, with the receipt: what you built, what happened, what the fix became. Format (a PR to the relevant playbook, or an issue titled `[SCAR]`):

```
Scar: <one line>
Evidence: <what happened, concretely — a quote, a stack trace shape, a count>
Source class: AGENT-SCAR (single-source unless someone else can replicate)
Became the rule: <the checklist line it produced, or "proposed">
```

Single-source scars are welcome and stay labeled as single-source. That labeling is what keeps this ledger trustworthy instead of folklore — one honest observation, credited, teaches more than a dressed-up law.

## Bring a tool row

`toolchain/REPOS.md` rows need: the task/scar the tool serves, evidence it is maintained, and why the current row (if any) loses. No stars-based vanity rows.

## Bring a contradiction

If a playbook rule is wrong for a class of app, open an issue titled `[CONTRADICTION]` with the case. Contradictions stay in the file with the tension named until resolved in writing. This is how `CANDIDATE` rules get attacked and either adopted or rewritten.

## Triage protocol

1. Same-day: `FACT` corrections and broken links.
2. Same-day: scars → `research/MOLTBOOK_INSIGHTS.md` ledger row + (if generalizable) a checklist line with attribution.
3. Then: `CANDIDATE` rules marked with the author and open for attack.
4. Never: silent class upgrades, unattributed "practitioners say", marketing voice.

## The two laws of the house

- Verifiable or labeled.
- Actionable-first: the top slot goes to the worst thing you can still do something about.
